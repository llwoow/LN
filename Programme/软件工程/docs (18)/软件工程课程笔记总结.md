## 1. 软件工程基础理论

### 1.1 软件工程定义与目标

**软件工程**是应用计算机科学、数学及管理科学的原理，以工程化原则和方法来开发与维护软件，把经过时间考验而证明正确的管理技术和当前能够得到的最好的技术方法结合起来，以经济地开发出高质量的软件并有效地维护它。

#### 🎯 核心目标
- **在既定时间、成本与质量约束下的可靠交付**
- **解决软件危机的核心问题**：控制成本、进度与质量
- **实现可维护性与可演化性**

### 1.2 软件生命周期(SDLC)

软件生命周期描述了软件从孕育到退役的完整过程，一般分为三大时期：

| 时期 | 主要阶段 | 关键活动 |
|------|----------|----------|
| **软件定义期** | 问题定义、可行性研究 | 确定目标、约束、可行性分析 |
| **软件开发期** | 需求分析、概要设计、详细设计、编码、测试 | 系统开发与质量构建 |
| **运行维护期** | 部署、运行维护 | 持续改进与演化 |

<details>
<summary><strong>💡 质量与过程的关系</strong></summary>

质量不是"测出来"的，而是在需求、设计、实现、验证与确认的各阶段通过过程控制与度量"构建出来"的。

- **测试模型**（如V模型）将验证与确认活动与开发阶段一一对应
- **度量指标**：缺陷密度、发现率、修复率、逃逸率与重复率
- **重要提醒**：避免将单一指标用于绩效考核，防止诱发不当行为
</details>

### 1.3 软件工程基本原则

| 原则 | 核心内涵 | 实践要点 |
|------|----------|----------|
| **抽象** | 提取本质特征，忽略细节 | 建立层次化模型 |
| **模块化** | 将系统分解为独立模块 | 高内聚、低耦合 |
| **信息隐藏** | 封装实现细节 | 接口与实现分离 |
| **一致性** | 统一的规范与标准 | 命名、编码、文档一致 |
| **完整性** | 覆盖所有功能需求 | 需求完整性检查 |
| **可验证性** | 便于测试与验证 | 可测试性设计 |

## 2. 软件生命周期模型

### 2.1 模型对比总览

| 模型 | 核心特征 | 适用场景 | 优缺点 |
|------|----------|----------|--------|
| **瀑布模型** | 线性顺序、阶段门禁、文档驱动 | 需求明确、变更少的项目 | ✅ 过程可控 ❌ 适应性差 |
| **V模型** | 开发与测试对称映射 | 质量与合规要求高 | ✅ 测试左移 ❌ 变更适应性差 |
| **敏捷模型** | 以人为核心、迭代增量 | 需求易变、小团队 | ✅ 快速响应 ❌ 大项目协调难 |
| **螺旋模型** | 风险驱动、每轮四象限 | 高风险、大中型系统 | ✅ 风险可控 ❌ 管理成本高 |
| **原型模型** | 以可演示原型澄清需求 | 需求不明确 | ✅ 需求澄清 ❌ 易演化为边做边改 |

### 2.2 瀑布模型详解

<details>
<summary><strong>📋 瀑布模型阶段详细说明</strong></summary>

#### 阶段与交付物

| 阶段 | 主要交付物 | 评审要点 |
|------|------------|----------|
| **规划与可行性** | 项目章程、可行性报告 | 目标一致性、资源与风险可接受性 |
| **需求分析** | 需求规格说明书(SRS) | 需求完整性、一致性、可测试性 |
| **概要设计** | 架构说明、接口设计 | 架构合理性、接口稳定性、可扩展性 |
| **详细设计** | 模块设计、算法说明 | 模块内聚/耦合、可实现性 |
| **编码** | 源代码、单元测试 | 规范符合度、覆盖率 |
| **测试** | 测试计划、用例、缺陷报告 | 覆盖率、缺陷收敛、质量门槛 |
| **维护** | 变更记录、补丁 | 变更影响评估、知识沉淀 |

#### 适用场景
- 需求明确、变更较少的项目
- 强合规行业（受监管的嵌入式与信息系统）
- 以合同与文档为交付契约的项目
</details>

### 2.3 V模型详解

V模型强调开发活动与验证/确认活动的对称映射：

| 开发阶段(左) | 对应测试阶段(右) | 验证/确认要点 |
|----------------|--------------------|----------------|
| 需求分析 | 系统测试 | 需求可追踪性、端到端场景覆盖 |
| 概要设计 | 集成测试 | 模块间接口契约、集成策略 |
| 详细设计 | 单元测试 | 模块内部逻辑、异常与边界条件 |
| 编码与构建 | 回归测试 | 变更影响面、缺陷不再现 |

### 2.4 敏捷模型详解

<details>
<summary><strong>🚀 敏捷实践与度量</strong></summary>

#### 敏捷实践—目标—度量

| 实践 | 目标 | 常见度量 |
|------|------|----------|
| **Sprint迭代** | 控制节奏、快速反馈 | 迭代速率、燃尽/燃起图 |
| **持续集成/交付** | 降低集成风险、快速验证 | 构建成功率、部署频率 |
| **自动化测试** | 提升回归效率与质量 | 自动化覆盖率、缺陷逃逸率 |
| **迭代评审/回顾** | 持续改进、风险早暴露 | 改进项完成率、重复问题减少率 |

#### 敏捷优势与挑战

**优势**：
- 缩短交付周期（实践中常见30%–40%的时间缩减）
- 提升客户反馈速度与风险早暴露

**挑战**：
- 对团队自组织与协作的高要求
- 对大型项目的协调复杂度提升
- 对优先级不明确或强合规场景的不适应性
</details>

### 2.5 数学公式与计算方法

#### PERT三点估算公式

$$\text{期望值: } E = \frac{O + 4M + P}{6}$$

$$\text{标准差: } \sigma = \frac{P - O}{6}$$

$$\text{方差: } \sigma^2 = \left(\frac{P - O}{6}\right)^2$$

其中：
- $O$ = 乐观时间
- $M$ = 最可能时间  
- $P$ = 悲观时间

#### COCOMO成本估算模型

**基本模型**：
$$\text{工作量: } E = a \times (KLOC)^b$$

$$\text{进度: } T = c \times (E)^d$$

其中$a$、$b$、$c$、$d$为模式参数，随模型层级与项目类型变化。

#### Walston-Felix模型

$$\text{工作量: } E = 5.2 \times (KLOC)^{0.91}$$

$$\text{持续时间: } D = 4.1 \times (KLOC)^{0.36}$$

$$\text{人员规模: } S = 0.54 \times E^{0.6}$$

## 3. 需求工程

### 3.1 需求工程概述

需求工程是一组迭代的活动集合，贯穿项目全生命周期：

| 阶段 | 目标 | 常用方法 | 关键产出 | 质量控制点 |
|------|------|----------|----------|------------|
| **获取** | 收集真实需求，理解业务 | 访谈、问卷、观察、头脑风暴 | 原始需求清单、场景描述 | 多源交叉验证、场景覆盖度检查 |
| **分析** | 澄清关系、消解冲突、优先级排序 | 需求分类、用例建模、可行性评估 | 结构化需求模型、优先级清单 | 一致性与完整性审查、可测试性评估 |
| **规格说明** | 标准化输出，成为协作契约 | 模板化编写、SRS结构化描述 | 软件需求规格说明书(SRS) | 可验证性、可追踪性、边界清晰 |
| **验证与确认** | 尽早发现错误，达成共识 | 评审会、原型验证、跟踪矩阵 | 评审纪要、问题清单、确认记录 | 缺陷密度、覆盖率、问题关闭率 |
| **变更管理** | 应对不可避免的变化 | 变更流程、影响分析、版本控制 | 变更记录、版本基线 | 审批合规性、影响分析质量 |

### 3.2 需求分类体系

| 分类 | 定义 | 示例 | 备注 |
|------|------|------|------|
| **功能需求** | 系统应执行的操作与行为 | 下单、支付、库存扣减 | 需明确输入/输出、异常与边界 |
| **非功能需求** | 系统应满足的质量属性与约束 | 响应时间≤200ms；99.9%可用 | 决定架构与技术选型 |
| **业务需求** | 组织的高层目标与价值 | 提升转化率、缩短交付周期 | 驱动系统范围与优先级 |
| **系统需求** | 为支撑业务需求所需的功能与质量 | 订单系统支持高并发扣减 | 映射到模块与接口 |
| **用户需求** | 特定角色在场景中的需求 | 收银员快速录入与折扣计算 | 用例驱动、可测试化 |

<details>
<summary><strong>📊 非功能需求质量属性度量示例</strong></summary>

| 质量属性 | 度量示例 | 验证方法 |
|----------|----------|----------|
| **性能** | P95响应时间≤200ms；峰值QPS≥5,000 | 压测、APM监控 |
| **可靠性** | 可用性≥99.9%；MTTR≤30min | 故障演练、HA测试 |
| **安全性** | 传输加密(TLS)；访问控制(RBAC) | 安全扫描、渗透测试 |
| **可用性** | UI操作步骤≤3；错误提示清晰 | 可用性测试、用户访谈 |
| **可维护性** | 代码规范、模块化；变更影响可控 | 静态分析、代码评审 |
| **兼容性** | 支持主流浏览器/移动端/接口版本 | 兼容性测试矩阵 |
</details>

### 3.3 UML建模

#### UML图类型与用途

| 图类型 | 用途 | 关键元素 | 常见错误 | 考试要点 |
|--------|------|----------|----------|----------|
| **类图** | 结构与关系建模 | 类、接口、属性、方法、关系、多重度 | 关系方向错误；多重度不合理 | 关系类型与多重度标注 |
| **对象图** | 实例结构展示 | 对象、冒号(:)、链 | 与类图混淆；实例关系不清 | 冒号表示实例；链表示关系 |
| **用例图** | 功能与参与者 | 参与者、用例、关联 | 参与者与系统边界不清 | 参与者识别与用例完整度 |
| **顺序图** | 时间序列交互 | 生命线、消息、激活 | 消息顺序错误；漏对象 | 对象与消息名称补全 |
| **状态图** | 状态与触发 | 初态、终态、状态、转换 | 触发条件遗漏；状态不闭合 | 状态与转换条件补全 |
| **活动图** | 流程与并发 | 活动、分叉、汇合、泳道 | 分叉/汇合错误；泳道边界不清 | 分叉线用途与泳道划分 |

#### UML关系类型与图形表示

| 关系 | 图形表示 | 含义 | 备注 |
|------|----------|------|------|
| **依赖** | 虚线箭头 | 使用关系，一者变化影响另一者 | 常用于临时使用 |
| **关联** | 实线 | 结构性联系 | 可带角色名与多重度 |
| **聚合** | 空心菱形 | 整体与部分的弱关系 | 部分可独立于整体 |
| **组合** | 实心菱形 | 强整体与部分关系 | 部分随整体消失 |
| **泛化** | 空心三角箭头 | 继承 | 子类替换父类 |
| **实现** | 虚线三角箭头 | 实现接口 | 接口定义行为契约 |

## 4. 系统设计与UML

### 4.1 设计原则(SOLID)

| 原则 | 核心概念 | 典型实践 | 常见反模式 |
|------|----------|----------|------------|
| **SRP** | 单一职责 | 类的职责单一化，避免"万能类" | 一个类承担多种变化原因 |
| **OCP** | 对扩展开放、对修改关闭 | 通过接口/抽象+多态实现扩展 | 改动基类影响大量子类 |
| **LSP** | 子类可替换基类 | 继承层级语义一致，行为可替换 | 违反父类契约的子类实现 |
| **ISP** | 接口隔离 | 拆分臃肿接口，按需依赖 | 强迫依赖不使用的方法 |
| **DIP** | 依赖倒置 | 面向抽象编程，依赖注入 | 高层直接依赖低层实现 |

### 4.2 架构设计风格

#### MVC/MVP/MVVM对比

| 模式 | 核心特点 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **MVC** | 控制器协调模型与视图 | 结构清晰，职责分明 | 控制器易"变胖"，耦合扩散 | 中等复杂度交互 |
| **MVP** | 主持人作为中间层 | 视图与模型解耦，易测 | Presenter接口与样板代码增多 | 高可测试性要求 |
| **MVVM** | 数据绑定与视图模型 | 同步简化，降低样板代码 | 学习曲线与绑定复杂性 | 前端复杂数据绑定场景 |

#### "4+1"视图模型

| 视图 | 关注点 | 典型工件 |
|------|--------|----------|
| **逻辑视图** | 功能与组件关系 | 类图、包图、领域模型 |
| **开发视图** | 代码组织与模块 | 模块划分、依赖关系图 |
| **进程视图** | 运行时进程与通信 | 顺序图、通信图、时序图 |
| **物理视图** | 部署拓扑与网络 | 部署图、节点与通信路径 |
| **场景视图** | 用例串联各视图 | 用例图、关键场景描述 |

### 4.4 耦合与内聚

#### 耦合类型（由高到低）

| 类型 | 定义 | 示例 | 风险等级 | 改进策略 |
|------|------|------|----------|----------|
| **内容耦合** | 直接使用内部数据/控制流程 | 直接修改另一个类的私有字段 | 极高 | 封装、接口化 |
| **公共耦合** | 共享全局数据结构 | 全局变量读写 | 高 | 减少共享，模块化 |
| **外部耦合** | 共享外部数据结构/格式 | 特定I/O格式耦合 | 中高 | 抽象接口、适配器 |
| **控制耦合** | 控制参数影响流程 | 传入布尔决定分支 | 中 | 策略模式替代 |
| **标记耦合** | 传递整个结构但只用部分 | 传入对象仅用少量字段 | 中低 | 拆分参数、提取所需 |
| **数据耦合** | 仅基本类型参数交互 | 函数参数为基本类型 | 低 | 保持数据耦合 |
| **无耦合** | 无直接依赖 | 理想 | 最低 | 维持模块独立 |

#### 内聚类型（由低到高）

| 类型 | 定义 | 示例 | 对维护性影响 |
|------|------|------|------------|
| **偶然内聚** | 元素无明显关联 | 随机工具函数堆叠 | 难以维护 |
| **逻辑内聚** | 逻辑分类组合 | switch分支 | 可读性差 |
| **时间内聚** | 同时段执行 | 启动时初始化 | 可接受但需拆分 |
| **过程内聚** | 按特定顺序执行 | 校验→转换→保存 | 结构较清晰 |
| **通信内聚** | 操作相同数据 | 对同一数据结构的不同操作 | 良好局部性 |
| **顺序内聚** | 输出为输入 | 流水线处理 | 高内聚 |
| **功能内聚** | 单一功能 | 纯业务函数 | 最高内聚 |

## 5. 软件测试与质量保证

### 5.1 测试基础与原则

<details>
<summary><strong>🧪 测试七大基本原则</strong></summary>

| 原则 | 核心内涵 | 实践要点 |
|------|----------|----------|
| **测试显示缺陷存在** | 测试目标是发现缺陷而非证明无错 | 以风险为导向设计测试；记录未覆盖风险与理由 |
| **无法证明无错** | 任何测试都不可能穷尽 | 设定合理的覆盖与质量门槛；持续改进测试组合 |
| **测试应尽早进行** | 缺陷越早发现成本越低 | 需求评审即定义验收标准与质量特性 |
| **穷尽测试不可行** | 资源有限需聚焦关键 | 优先覆盖关键路径与高风险模块 |
| **避免偏见** | 保持客观与多元视角 | 引入独立评审与交叉测试 |
| **避免自我测试** | 开发者对自身代码存在盲区 | 实施独立测试与代码审查 |
| **测试基于需求** | 每项测试都应有需求依据 | 建立需求—用例—缺陷的可追溯链 |
</details>

### 5.2 测试分类与策略

#### 测试层次对比

| 测试层次 | 定义 | 目标 | 对象 | 时机 | 典型缺陷 | 常见误区 |
|----------|------|------|------|------|----------|----------|
| **单元测试** | 对最小可测单元进行验证 | 逻辑与结构正确性 | 代码单元 | 编码后即时 | 边界条件错误、异常处理缺失 | 过度关注覆盖率数字而忽略关键路径 |
| **集成测试** | 验证模块/服务间的接口与契约 | 接口正确性与交互稳定性 | 模块间接口 | 单元测试后 | 协议不匹配、数据格式不一致 | 跳过接口契约测试，直接跳至系统测试 |
| **系统测试** | 对完整集成系统进行整体验证 | 符合需求与质量特性 | 完整系统 | 集成测试通过后 | 性能瓶颈、兼容性问题 | 以E2E替代系统测试，导致反馈慢与脆弱 |
| **验收测试** | 确认系统满足业务与合同要求 | 交付可行性与用户认可 | 业务流程 | 系统测试后 | 需求偏差、交付标准不清 | 缺乏明确的验收依据与场景 |
| **回归测试** | 验证变更未破坏已有功能 | 稳定性与防回归 | 关键功能 | 每次变更后 | 修复引入新缺陷、隐藏回归 | 只回归"看似相关"的功能，遗漏耦合点 |
| **端到端测试** | 模拟真实用户场景的完整流程 | 业务闭环与跨系统交互 | 用户旅程 | 系统测试后 | 跨系统数据一致性问题 | 过多UI级E2E，导致维护成本与Flaky高 |
| **冒烟测试** | 构建门禁，验证关键功能可运行 | 快速判定构建质量 | 关键路径 | 每次构建后 | 构建失败、关键路径不可用 | 冒烟用例过多过慢，失去门禁意义 |

### 5.5 覆盖与充分性度量

#### 覆盖类型对比

| 覆盖类型 | 定义 | 计算 | 严格度 | 优点 | 局限 |
|----------|------|------|--------|------|------|
| **语句覆盖** | 每条可执行语句至少执行一次 | 已执行语句/总语句 | 低 | 简单、易实现 | 漏分支与条件 |
| **分支覆盖** | 每个判定的真/假分支均覆盖 | 已覆盖分支/总分支 | 中 | 比语句覆盖更严格 | 不含复合条件内部 |

### 6.2 进度管理：关键路径法(CPM)

<details>
<summary><strong>⏰ CPM核心参数与计算步骤</strong></summary>

#### 时间参数与公式
- **最早开始(ES)**: 任务能够开始的最早时间
- **最早完成(EF)**: $EF = ES + 持续时间$
- **最晚开始(LS)**: 在不延误项目的前提下，任务能够开始的最晚时间
- **最晚完成(LF)**: 在不延误项目的前提下，任务能够完成的最晚时间
- **总浮动时间(TF)**: $TF = LS - ES = LF - EF$，关键路径上TF=0
- **自由浮动时间(FF)**: 在不影响后续任务最早开始的前提下，任务可延迟的时间

#### 计算步骤
1. **绘制网络图**: 按依赖关系(FS/SS/FF等)构建任务网络
2. **正推法计算ES/EF**: 从起点开始，按依赖关系依次计算每个任务的最早时间
3. **逆推法计算LS/LF**: 从终点回溯，按依赖关系依次计算每个任务的最晚时间
4. **计算总浮动时间并识别关键路径**: TF=0的路径为关键路径
5. **验证与优化**: 结合资源约束与风险，动态调整关键任务资源与缓冲

#### 依赖类型
- **FS(Finish-to-Start)**: A完成→B开始，最常见
- **SS(Start-to-Start)**: A开始→B开始，适用于并行启动
- **FF(Finish-to-Finish)**: A完成→B完成，适用于并行收尾
</details>

#### CPM示例计算

| 任务 | 持续时间 | 前置 | ES | EF | LS | LF | TF |
|------|----------|------|----|----|----|----|----|
| A 需求分析 | 3 | —— | 0 | 3 | 0 | 3 | 0 |
| B 原型设计 | 5 | A | 3 | 8 | 3 | 8 | 0 |
| C 前端开发 | 8 | B | 8 | 16 | 8 | 16 | 0 |
| D 后端开发 | 7 | B | 8 | 15 | 9 | 16 | 1 |
| E 测试与调试 | 4 | C, D | 16 | 20 | 16 | 20 | 0 |
| F 上线部署 | 2 | E | 20 | 22 | 20 | 22 | 0 |

**解读**: 关键路径为A→B→C→E→F，总工期22天；D有1天总浮动时间。

### 6.3 进度管理：计划评审技术(PERT)

#### 三点估算与分布假设

$$\text{期望工期: } Te = \frac{O + 4M + P}{6}$$

$$\text{标准差: } \sigma = \frac{P - O}{6}$$

$$\text{方差: } \sigma^2 = \left(\frac{P - O}{6}\right)^2$$

其中：
- $O$ = 乐观时间
- $M$ = 最可能时间
- $P$ = 悲观时间

#### PERT三点估算示例

| 活动 | O | M | P | 期望Te | 标准差σ |
|------|---|---|---|--------|---------|
| 需求澄清 | 3 | 5 | 11 | 5.33 | 1.33 |
| 组件开发 | 4 | 6 | 10 | 6.33 | 1.00 |
| 集成测试 | 2 | 4 | 8 | 4.33 | 1.00 |

### 6.4 成本估算：功能点方法(FPA)

<details>
<summary><strong>💰 FPA五要素与计算流程</strong></summary>

#### 五类功能要素
- **外部输入处理(External Input, EI)**: 面向用户输入数据的处理过程
- **外部输出处理(External Output, EO)**: 面向用户输出报表/票据等处理过程
- **外部查询处理(External Inquiry, EQ)**: 面向用户查询的检索与响应过程
- **内部逻辑文件(Internal Logical File, ILF)**: 系统内部持久化的逻辑数据文件
- **外部接口文件(External Interface File, EIF)**: 与其他系统交换数据的接口文件

#### 计算流程
1. **事务功能(EI/EO/EQ)**与**数据功能(ILF/EIF)**需按复杂度分级(简单/一般/复杂)
2. **未调整功能点(UFP)**为各要素按复杂度对应的功能点之和
3. **值调整因子(VAF)**由14项通用系统特征的总影响程度(TDI)计算：
   $$VAF = (TDI \times 0.01) + 0.65$$
4. **调整后功能点**: $DFP = UFP \times VAF$
5. **工作量与成本**: 工作量 = 软件系统规模 ÷ 生产定额；系统成本 = 工作量 × 人日单价
</details>

#### VAF计算示例

| 指标 | 数值/说明 |
|------|----------|
| **TDI**(14项通用系统特征合计) | 例如14 |
| **VAF** | $(14 \times 0.01) + 0.65 = 0.79$ |
| **UFP**(示例) | 1000 |
| **调整后功能点 DFP** | $1000 \times 0.79 = 790$ |

### 6.5 成本估算：COCOMO模型

#### 模型类型与公式

**基本模型(单变量)**：
$$\text{工作量: } E = a \times (KLOC)^b$$

$$\text{开发时间: } D = c \times E^d$$

**中间模型(引入工作量调节因子EAF)**：
$$\text{工作量: } E = a \times (KLOC)^b \times EAF$$

其中$EAF$为各成本驱动因子Fi的乘积：$EAF = \prod Fi(i=1..15)$

#### COCOMO案例估算(CAD软件)

| 项目 | 数值/说明 |
|------|----------|
| **规模(KLOC)** | 33.2 |
| **项目类型** | 中等规模，半独立型 |
| **经验常数** | a=3.0, b=1.12, c=2.5, d=0.35 |
| **工作量E** | 152 人月 |
| **开发时间D** | 14.5 月 |
| **项目人数** | 约11人($E \div D$) |

| 策略 | 定义 | 适用场景 | 示例 |
|------|------|----------|------|
| **规避** | 改变计划或目标以消除风险 | 风险影响过大 | 采用成熟技术、迭代式开发 |
| **减轻** | 降低风险发生概率或影响 | 风险可控 | 增加测试覆盖、技术培训 |
| **转移** | 通过合同、保险或外包转移风险 | 第三方可更好处理 | 外包、保险 |
| **接受** | 评估后认为影响可接受 | 风险影响小或处理成本高 | 制定应急预案与触发条件 |

#### 定量评估方法

**LS法(风险矩阵)**:
$$R = L \times S$$
其中L为可能性，S为后果严重性，R值越大风险越高。

**LEC法(作业条件危险性分析)**:
$$D = L \times E \times C$$
其中L为可能性，E为暴露频繁程度，C为后果，D值越大危险性越高。

### 6.7 软件度量体系

<details>
<summary><strong>📊 六大类关键指标与公式</strong></summary>

#### 产品完成度
- **需求通过率**: 已通过需求 / 已计划需求
- **功能点通过率**: 已通过功能点 / 已测试功能点

#### 产品质量
- **测试通过率**: 已通过测试 / 计划执行测试
- **缺陷密度**: 缺陷总数 / 千行代码数
- **缺陷严重级别分布**: 某级别缺陷数 / 缺陷总数
- **缺陷修复率**: 已修复缺陷数 / 缺陷总数

#### 测试完成度
- **用例覆盖率**: 已设计用例数 / 计划设计用例数
- **测试执行率**: 已执行测试数 / 计划执行测试数

#### 研发过程质量
- **缺陷生存周期**: 缺陷生存总时长 / 缺陷数
- **测试用例命中率**: 缺陷数量 / 用例数量
- **二次故障率**: 缺陷二次重开数量 / 缺陷总数量
- **缺陷有效率**: 有效缺陷数量 / 缺陷总数量
- **缺陷探测率**: 某级别发现缺陷数 / (总体缺陷数 + 交付后新增缺陷数)

#### 计划偏离
- **工作量偏离**: (实际工作量 − 计划工作量) / 计划工作量

#### 产品质量趋势
- **缺陷到达率**: 缺陷数量 / 时间周期
- **缺陷收敛度**: 遗留缺陷数量 / 时间周期
- **缺陷引入率**: 新增缺陷数量 / 新增千行代码数
</details>

### 6.8 考试计算题：挣值管理(EVM)

<details>
<summary><strong>💹 EVM核心公式与计算</strong></summary>

#### 基本量
- **PV**(计划价值): 按计划应完成工作的价值
- **EV**(挣值): 实际完成工作的价值
- **AC**(实际成本): 实际花费
- **BAC**(完工预算): 预算总额

#### 偏差与指数
- **成本偏差**: $CV = EV - AC$
- **进度偏差**: $SV = EV - PV$
- **成本绩效指数**: $CPI = EV / AC$
- **进度绩效指数**: $SPI = EV / PV$

#### 完工估算
**非典型偏差**(剩余工作按计划):
$$ETC = BAC - EV$$
$$EAC = AC + ETC$$

**典型偏差**(延续当前绩效):
$$ETC = \frac{BAC - EV}{CPI}$$
$$EAC = \frac{BAC}{CPI}$$

#### 完工偏差与绩效指数
- **完工偏差**: $VAC = BAC - EAC$
- **待完成绩效指数(TCPI)**:
  - 基于BAC: $TCPI = \frac{BAC - EV}{BAC - AC}$
  - 基于EAC: $TCPI = \frac{BAC - EV}{EAC - AC}$
</details>

#### EVM示例

| 指标 | 数值 |
|------|------|
| **预算总额(BAC)** | 100 万元 |
| **累计支出(AC)** | 60 万元 |
| **计划完成百分比** | 40% |
| **实际完成百分比** | 30% |
| **PV** | 40 万元 |
| **EV** | 30 万元 |
| **CPI** | 0.5 |
| **SPI** | 0.75 |
| **CV** | −30 万元 |
| **SV** | −10 万元 |
| **ETC**(典型偏差) | 140 万元 |
| **TCPI**(基于BAC) | 1.75 |

**解读**: 当前成本与进度绩效均不佳；若延续当前绩效，完工估算EAC = 200万元，VAC = −100万元；TCPI显示剩余工作的效率要求显著高于既往水平。

### 7.2 软件演化规律

#### Lehman定律
1. **持续变化定律**: 实际使用的程序必须不断演化，否则会越来越不符合实际需求
2. **复杂性递增定律**: 程序演化的过程中，其复杂性会不断增加，必须进行结构化设计来控制
3. **持续增长定律**: 程序的功能必须不断增长以满足用户需求
4. **质量下降定律**: 程序质量会随演化而下降，必须进行维护以保持质量
5. **反馈系统定律**: 大型程序的演化是一个多回路的反馈系统

### 8.2 核心公式汇总

<details>
<summary><strong>🧮 完整公式速查表</strong></summary>

#### 进度管理
- **PERT三点估算**: $Te = \frac{O + 4M + P}{6}$, $\sigma = \frac{P - O}{6}$
- **CPM计算**: $EF = ES + 持续时间$, $TF = LS - ES = LF - EF$
- **CPM正推**: $EF = ES + duration$, $ES = max(EF_{predecessors})$
- **CPM逆推**: $LS = LF - duration$, $LF = min(LS_{successors})$

#### 成本估算
- **COCOMO基本模型**: $E = a \times (KLOC)^b$, $D = c \times (E)^d$
- **COCOMO中间模型**: $E = a \times (KLOC)^b \times EAF$
- **Walston-Felix**: $E = 5.2 \times (KLOC)^{0.91}$, $D = 4.1 \times (KLOC)^{0.36}$, $S = 0.54 \times E^{0.6}$
- **FPA计算**: $DFP = UFP \times VAF$, $VAF = (TDI \times 0.01) + 0.65$

#### 挣值管理
- **基本量**: $PV, EV, AC, BAC$
- **偏差**: $CV = EV - AC$, $SV = EV - PV$
- **绩效指数**: $CPI = EV / AC$, $SPI = EV / PV$
- **完工估算**: $EAC = \frac{BAC}{CPI}$, $ETC = EAC - AC$, $VAC = BAC - EAC$
- **TCPI**: $TCPI = \frac{BAC - EV}{BAC - AC}$ 或 $TCPI = \frac{BAC - EV}{EAC - AC}$

#### 质量度量
- **缺陷密度**: $DD = \frac{缺陷数}{规模}$ (KLOC或功能点)
- **发现率**: $DR = \frac{缺陷数}{时间}$
- **修复率**: $FR = \frac{修复缺陷数}{时间}$

#### 风险管理
- **LS法**: $R = L \times S$
- **LEC法**: $D = L \times E \times C$
- **沟通渠道**: $N \times (N - 1) / 2$

#### 项目度量
- **生产率**: $\frac{产出}{投入}$ (功能点/人月, KLOC/人月)
- **质量**: $\frac{缺陷数}{规模}$, $\frac{测试通过数}{总测试数}$
